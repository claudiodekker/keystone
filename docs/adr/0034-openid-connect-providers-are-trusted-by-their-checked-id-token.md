# OpenID Connect providers are trusted by their checked ID token

`keystone-oauth` trusts a plain OAuth 2 provider by asking its API who an access token belongs to (ADR 0032), and accepts its sudo answer without knowing when the user last signed in (ADR 0033). An OpenID Connect provider issues an ID token that says who the user is, who the token is for, and when the user signed in. OpenID Connect Core 1.0 section 3.1.3.7 lists the checks a client must make on it, and ASVS 5.0 V6.8.4 asks a relying party to check that the provider authenticated the user as recently as it asked. This decides how Keystone trusts a provider listed with `issuer`.

- **Keystone checks every ID token's signature against the issuer's JWKS.** OpenID Connect lets a client that got the token straight from the token endpoint over TLS skip the signature check. Keystone checks it anyway, with `firebase/php-jwt`, so its trust in a token never depends on how the token arrived. The token must use the algorithm its key names in the JWKS, and a key that names none is read as RS256. Shared-secret (HS) keys are dropped, since anyone who reads the JWKS would hold them. A token whose header names no key is checked against the JWKS's only key, as OpenID Connect Core section 10.1 allows. It then checks `exp` and `iat` with 60 seconds of leeway, `iss` against the configured issuer, `aud` and `azp` against the client id, the `nonce` the ceremony slot kept, and `sub`. A failed check is a failed callback with its own reason.
- **Discovery and the JWKS are fetched on every return, and nothing is cached.** A return already makes a request to the token endpoint, and two more GETs cost little next to a user's trip to the provider. A provider that rotates its keys is picked up on the next return, and Keystone keeps no cache an attacker could poison or an operator would have to clear. Both requests go through the `guzzle` options Socialite gives the provider's driver, so an app's proxy settings and the AppTests' fake apply to them too. They time out after 5 seconds unless those options say otherwise. The JWKS must be `https`, and redirects are followed to `https` only, since an attacker on the network who could serve the JWKS could name any subject. The JWKS isn't bound to the issuer's host, because Google serves its keys from `googleapis.com`. A discovery document that names another issuer is an outage, not a wrong answer: the return is reported, refused with `keystone.verify_failed` and not counted.
- **The subject comes from the ID token, and userinfo is never asked.** The ID token is signed and bound to this authorization by its nonce. A userinfo answer is neither, so it adds a request and nothing Keystone could check.
- **The RFC 9207 `iss` parameter is required only when the provider announces it.** A return's `iss` parameter must match the issuer whenever it is present, which stops a mix-up between two listed providers. A provider whose discovery document sets `authorization_response_iss_parameter_supported` must send it. Many providers predate RFC 9207 and send nothing, and the nonce and the ID token's `iss` claim already bind their returns to the issuer.
- **Sudo compares `auth_time` with the start of the redirect.** Sudo sends `max_age=0`. The ceremony slot keeps the time the sudo redirect started, and the ID token's `auth_time` must be no earlier, with 30 seconds of leeway for clock skew between Keystone and the provider. That is half the token's own leeway, because each second of it is a second in which a provider that ignores `max_age=0` passes sudo on an old session. A missing or older `auth_time` is refused as `oauth.stale_sign_in`. Signing in and connecting an account send no `max_age` and don't check `auth_time`.

The alternative to checking each token was Socialite's own `userFromToken()`. Most drivers answer it from userinfo, and the Google driver, given an ID token, checks its signature, issuer and audience but no nonce or `auth_time`. It lost because a token from another authorization, or a stale sign-in, would pass. A second alternative, caching the JWKS for its HTTP cache lifetime, lost because a short-lived cache saves two requests per sign-in and adds a key-rotation failure mode. A third, refusing any return without an `iss` parameter, lost because it would refuse every provider that predates RFC 9207.

## Consequences

- A provider listed with `issuer` must publish discovery and a JWKS at its issuer URL, sign its ID tokens with a key from that JWKS, and include the `openid` scope. Boot refuses an `issuer` that isn't an `https` URL without query or fragment, or one listed without `openid`.
- An OpenID Connect provider that can't be reached for discovery or its JWKS can't sign anyone in. Its returns are refused as `keystone.verify_failed` and reported.
- Sudo through an OpenID Connect provider proves a fresh sign-in, which closes the ASVS V7.5.1 and V6.8.4 deviation ADR 0033 accepts. Plain OAuth 2 providers stay under ADR 0033.
- `keystone-oauth` depends on `firebase/php-jwt`, which Socialite already requires.
