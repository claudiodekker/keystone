# Emailed links carry their token in the URL

ASVS 5.0 V14.2.1 asks that sensitive data travel only in the message body or headers, never in the URL or its query string. An emailed link can't follow it: the mail client opens a URL, so whatever proves the link must be in that URL. Registration links do, and so will address verification, recovery, magic links, sudo links and inbox proof, which all go through `EmailedLinks`. **Keystone accepts this as a deviation from V14.2.1** and narrows what a leaked URL is worth instead.

- **The URL is built on `app.url`, never on the request's host.** `EmailedLinks::issue()` takes the scheme, host, port and path from `app.url`, and only the route's path under it from the router, so an app served under a path gets links under that path. A request that names another `Host` or `X-Forwarded-Host` still gets a link to the app, and a link presented anywhere else is refused, because `verify()` compares the request's root (scheme, host, port and base path) with `app.url`'s before anything else. Behind a proxy the app must trust its proxies so the two agree.
- **The token is encrypted, and the signature covers where it may be used.** The query holds `expires`, `token` and `signature`. `token` is the kind's payload as JSON, encrypted with AES-256-GCM by an `Encrypter` that holds only the subkey `keystone.emailed-link.payload.{purpose}` of the current app key, so the address or account it names never appears in clear. `signature` is an HMAC over `app.url`, the route's path, `expires` and `token`, under the subkey `keystone.emailed-link.sign.{purpose}`. Each role has its own fixed prefix, and the digest of a spent link its own label, `keystone.emailed-link.digest`, so no purpose can name another role's key. Both subkeys come from `Hmac::subkey()`, which derives only from the current key: Laravel's `Crypt` would also try `app.previous_keys`, so a fresh `Encrypter` stands in for it. A link signed before an `APP_KEY` rotation fails. The payload is decoded with `json_decode` and parsed by its kind; it is never unserialized.
- **Opening a link changes nothing.** The GET renders a page with one button and spends nothing, so a mail scanner or a link preview leaves the link working. A GET for a link that no longer holds records `request.rejected` like any other refusal; the recorder's anonymous log cooldown bounds those lines. Only that button's POST, to the same URL, spends the link. Both send `Referrer-Policy: no-referrer`, so no request the page makes carries the URL to another site. The link's controller declares this as route middleware (`Controller::noReferrer()`) that runs before the request limit and the registration gate, so a throttle refusal, a closed-registration redirect or a signed-in refusal at the link's URL sends it too. The middleware sets a request attribute the floor middleware reads last, so the stricter value wins over the floor's without the floor knowing any link's route, and `EmailedLinks` knows nothing of headers.
- **Every link works once, for 10 minutes.** The POST stores an HMAC digest of the signature in `used_email_links`, with the link's expiry, before it looks anything up. A second insert of the same digest affects no row, and the link is refused as used. The digest is stored with `insertOrIgnore` on the user model's connection, which behaves the same on SQLite, PostgreSQL and MySQL and needs no cache. Expired digests are pruned hourly. The lifetime is a constant, not a setting.
- **Every refusal looks the same.** A link that is changed, expired, undecryptable, used, presented on another host, or whose destination no longer qualifies (checked by one rule before mailing and again when spent, and handed back to the kind when it fails) sends the user to the kind's "link expired" step and records `request.rejected` with a reason for the operator. The user learns nothing about which check failed.

## Consequences

- The URL, token included, can still land in places the app doesn't control: the mail provider, the browser's history, and the access log of any proxy or server in front of the app. Each copy is worthless once the link is spent or 10 minutes have passed, and none shows the address.
- Rotating `APP_KEY` ends every link in flight. Users ask for a new one.
- An app whose trusted-proxy setup doesn't let Laravel see `app.url`'s scheme and host refuses every link. The docs say so where links are introduced.
- A kind of link is one class implementing `EmailedLink`. It declares its purpose, route, payload and destination check, and never sees a key, signature or table. The interface is `@internal`, so a later kind may add a method, such as one binding a link to the browser that asked for it, without breaking apps.
