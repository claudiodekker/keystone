# Emailed links carry their token in the URL

ASVS 5.0 V14.2.1 asks that sensitive data travel only in the message body or headers, never in the URL or its query string. An emailed link can't follow it: the mail client opens a URL, so whatever proves the link must be in that URL. Registration links do, and so do address verification, recovery, magic links, sudo links and inbox proof. **Keystone accepts this as a deviation from V14.2.1** and narrows what a leaked URL is worth instead.

- **The URL is built on `app.url`, never on the request's host.** The scheme, host, port and path come from `app.url`, and only the route's path under it from the router, so an app served under a path gets links under that path. A request that names another `Host` or `X-Forwarded-Host` still gets a link to the app, and a link presented anywhere else is refused, because the request's root (scheme, host, port and base path) is compared with `app.url`'s before anything else. Behind a proxy the app must trust its proxies so the two agree.
- **The token is encrypted, and the signature covers where it may be used.** The query holds `expires`, `token` and `signature`. `token` is the kind's payload as JSON, encrypted with AES-256-GCM under a per-purpose subkey of the current app key, so the address or account it names never appears in clear. `signature` is an HMAC over `app.url`, the route's path, `expires` and `token`, under its own per-purpose subkey. Each role has its own fixed prefix, and the digest of a spent link its own label, so no purpose can name another role's key. Both subkeys derive only from the current key, never from `app.previous_keys`, so a link signed before an `APP_KEY` rotation fails. The payload is decoded as JSON and parsed by its kind; it is never unserialized.
- **Opening a link spends nothing.** The GET renders a page with one button and spends nothing, so a mail scanner or a link preview leaves the link working. It refuses a link that is already spent, so the page never reports a proof the button can no longer use. A GET for a link that no longer holds records `request.rejected` like any other refusal; the recorder's anonymous log cooldown bounds those lines. Only that button's POST, to the same URL, spends the link. The two kinds of magic link, the sign-in link and the sudo link, are the exception and have no button. RFC 9110 section 9.2.1 calls GET safe because "the client does not request, and does not expect, any state change on the origin server as a result of applying a safe method to a target resource", so that "automated retrieval processes (spiders) and cache performance optimization (pre-fetching)" can work "without fear of causing harm". A magic link's GET spends it all the same, and that harm still can't happen, because the GET spends only in the browser whose ceremony slot holds the link's token. A scanner or preview never holds that browser's session, so its GET is refused and spends nothing, and the link keeps working. The only GET that changes state is the user's own, in the browser where they asked for exactly that. The inbox proof link is bound to its browser too, but keeps its button. The page and the POST both send `Referrer-Policy: no-referrer`, so no request the page makes carries the URL to another site, and so does every refusal at the link's URL, such as a throttle refusal, a closed-registration redirect or a signed-in refusal. This value wins over the hardening floor's.
- **Every link works once, for 10 minutes.** The POST stores an HMAC digest of the signature in `used_email_links`, with the link's expiry, before it looks anything up. A second insert of the same digest affects no row, and the link is refused as used. This behaves the same on SQLite, PostgreSQL and MySQL and needs no cache. Expired digests are pruned nightly, with the other retention prunes, which is soon enough because a row only matters until its link expires. The lifetime is a constant, not a setting.
- **Every refusal looks the same.** A link that is changed, expired, undecryptable, used, presented on another host, or whose destination no longer qualifies (checked by one rule before mailing and again when spent) sends the user to the kind's "link expired" step and records `request.rejected` with a reason for the operator. The user learns nothing about which check failed.

## Consequences

- The URL, token included, can still land in places the app doesn't control: the mail provider, the browser's history, and the access log of any proxy or server in front of the app. Each copy is worthless once the link is spent or 10 minutes have passed, and none shows the address.
- Rotating `APP_KEY` ends every link in flight. Users ask for a new one.
- An app whose trusted-proxy setup doesn't let Laravel see `app.url`'s scheme and host refuses every link. The docs say so where links are introduced.
