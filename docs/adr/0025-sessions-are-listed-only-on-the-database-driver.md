# Sessions are listed only on the database driver

ASVS 5.0 V7.5.2 asks that users can view their active sessions and, after authenticating again, end any or all of them. Keystone signs out every other session on every session driver, because that only moves the credential epoch (ADR 0005, ADR 0014). Listing sessions and ending one of them needs a store Keystone can read every session of an account from. Of Laravel's drivers, only `database` keeps one: a table with each session's id, `user_id`, IP address, user agent and last activity. The `file`, `cookie`, `redis` and other drivers have no index by account, and a cookie session lives only in its browser.

- **On every other driver the list is unavailable, and that is an accepted deviation from V7.5.2.** The security page shows the `sessions-unavailable` status in place of the list, and revoking one session is refused with the same status. Boot doesn't fail, because an app on the `file` or `redis` driver is a supported setup, and the user can still sign out every other session. Keeping our own index of sessions beside the app's driver was rejected: it would be a second record of the same sessions, written on every request, that drifts from the driver whenever the two disagree about what is alive.
- **The handler the request uses decides, not the config.** Sessions are listed only when the request's session handler is Laravel's database handler. Reading the handler, not `session.driver`, follows what the app actually runs, including a test that swaps the driver and an app driver that extends the database handler.
- **A row is listed when its row and its payload both say it is live.** The account's rows (`user_id`) that were active within `session.lifetime` and since the last epoch move are read, newest first, at most 49 besides this one. Each is kept only when its payload signs in this account on the account's current credential epoch. The row filter keeps dead rows from taking places in the list. The payload check is exact: it hides a row written after an epoch move by a request that began before it, and a row whose `user_id` disagrees with its payload.
- **The payload is read the way the app's driver reads it.** It is decrypted and unserialized as the app's store does, with `session.encrypt` and `session.serialization = json` included, so Keystone never decodes Laravel's format itself. Reading another session must not disturb the request's own: Laravel's database handler remembers whether it read a row, and a read through the request's own handler would make the request update the row of an id that a rotation earlier in the request left with no row, losing the user's session.
- **This device comes from the request, never from its row.** Its row holds the previous request's IP address and user agent, and has no row at all right after a rotation. The list shows the request's own context and "now".
- **A handle names a session outside Keystone.** It is an HMAC of the session id under its own subkey of the app key, as the rate limiter's keys are (ADR 0007). A handle is looked up by comparing it in constant time against the handles of the account's live sessions, so it can only name a session the user could see. The session id itself never leaves Keystone.
- **Revoking one session goes through the account change and moves no epoch.** This device can't be revoked. Revoking forgets the remember token the session stored, scoped to the account because the token id came from a stored payload, and records `session.revoked` with the revoked session's IP address and user agent under this request's path and id. The session's row is deleted after the commit, as signing out every other session deletes theirs.

## Consequences

- Rendering the security page reads up to 49 session payloads on the `database` driver, and looks up the location of each distinct IP address in the request.
- A revoked browser with a request in flight survives when that request rotates its id, because its new row is inserted with a live payload. The epoch doesn't move for one session, so nothing else ends it. Signing out every other session has no such gap.
- The list depends on Laravel writing `user_id` from the default guard, which is the Keystone guard after installation. With another default guard the list is empty but for this device.
- An app on another driver that needs the list switches to `database`. Keystone offers no setting to list sessions from another store.
