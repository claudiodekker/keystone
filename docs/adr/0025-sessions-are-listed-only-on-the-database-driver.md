# Sessions are listed only on the database driver

ASVS 5.0 V7.5.2 asks that users can view their active sessions and, after authenticating again, end any or all of them. Keystone signs out every other session on every session driver, because that only moves the credential epoch (ADR 0013, ADR 0014). Listing sessions and ending one of them needs a store Keystone can read every session of an account from. Of Laravel's drivers, only `database` keeps one: a table with each session's id, `user_id`, IP address, user agent and last activity. The `file`, `cookie`, `redis` and other drivers have no index by account, and a cookie session lives only in its browser.

- **On every other driver the list is unavailable, and that is an accepted deviation from V7.5.2.** The security page shows the `sessions-unavailable` status in place of the list, and revoking one session is refused with the same status. Boot doesn't fail, because an app on the `file` or `redis` driver is a supported setup, and the user can still sign out every other session. Keeping our own index of sessions beside the app's driver was rejected: it would be a second record of the same sessions, written on every request, that drifts from the driver whenever the two disagree about what is alive.
- **The guard decides by the handler instance.** `KeystoneGuard::sessions()` returns an `AccountSessions` only when the request's store is a `Store` whose handler is a `DatabaseSessionHandler`, and `null` otherwise. Every unavailable branch hangs off that `null`. Reading the handler, not `session.driver`, follows what the app actually runs, including a test that swaps the driver and an app driver that extends the database handler.
- **A row is listed when a prefilter and its payload both say it is live.** The SQL keeps the account's rows (`user_id`) that were active within `session.lifetime` and since `credential_epoch_moved_at`, newest first, at most 49 besides this one. Each is then read through Laravel's own store, and kept only when its login key holds this account and its epoch key equals the account's `credential_epoch`. The prefilter keeps dead rows from taking places in the list. The payload check is exact: it hides a row written after an epoch move by a request that began before it, and a row whose `user_id` disagrees with its payload. The guard passes the key names to `AccountSessions` as values, so the keys are still derived in the guard alone (ADR 0005).
- **The payload is read through a clone of the store with a clone of its handler.** The cloned store decrypts and unserializes the payload as the app's driver does, with `session.encrypt` and `session.serialization = json` included, so Keystone never decodes Laravel's format itself. The handler is cloned because `DatabaseSessionHandler::read()` sets its `exists` flag. Read through the request's own handler, that flag would make the request update the row of an id that a rotation earlier in the request left with no row, and the user's session would be lost. The clone is flushed before it starts, because `Store::start()` merges what it reads into what it holds, and a row that reads as empty would otherwise look like this session. A unit test pins both under encryption and JSON serialization.
- **This device comes from the request, never from its row.** Its row holds the previous request's IP address and user agent, and has no row at all right after a rotation. The list shows the request's own context and "now".
- **A handle names a session outside Keystone.** It is an HMAC of the session id under the `keystone.session-handle` subkey of the app key, through the same `Hmac::make()` the rate limiter's keys use (ADR 0007). A handle is looked up by comparing it with `hash_equals` against the handles of the account's live sessions, so it can only name a session the user could see. The session id itself stays inside `AccountSessions`.
- **Revoking one session goes through the account change and moves no epoch.** `AccountChange::revokeSession()` refuses this device with `CurrentSession`, forgets the remember token the session stored inside the transaction, scoped to the account because the token id came from a stored payload, and records `session.revoked` with the revoked session's IP address and user agent under this request's path and id. The row is deleted after the commit, in `AccountChanges::committed()`, after the mover's session is carried over and before the events are recorded, the same step that deletes the rows of signing out every other session.

## Consequences

- Rendering the security page reads up to 49 session payloads on the `database` driver, and looks up the location of each distinct IP address in the request.
- A revoked browser with a request in flight survives when that request rotates its id, because its new row is inserted with a live payload. The epoch doesn't move for one session, so nothing else ends it. Signing out every other session has no such gap.
- The list depends on Laravel writing `user_id` from the default guard, which is the Keystone guard after installation. With another default guard the list is empty but for this device.
- An app on another driver that needs the list switches to `database`. Keystone offers no setting to list sessions from another store.
