# The sudo gate throws from three doors and the replay reuses the sign-in surfaces

ADR 0021 made sudo a session value the guard owns. This decides how a request without it is refused, and how a session earns it back. Two things must hold: nothing gated can be reached without a live grant, whatever an app replaces, and earning a grant must ask exactly what a sign-in would, so a stolen session with a password alone never clears an account that holds a second factor.

- **One gate, which throws.** `SudoGate::enforce()` is the only place the decision is made: a guest is refused before any grant is read, because Laravel's own `logout()` leaves the session's data behind; a live grant from its own subnet passes; a live grant from another subnet is revoked, recorded as `sudo.network_changed` and alerted; anything else starts a sudo-in-progress and throws `SudoRequired`. It throws rather than returns, so no caller can take its answer and carry on. The exception renders itself through `RespondToSudoRequired`, a 403 for a JSON client and a redirect to the sudo page otherwise, which is the one swappable piece: the response, never the decision.
- **Three doors to the same gate.** Apps gate their routes with the `sudo` middleware alias. A core controller that needs sudo lists `static::sudo()` in its middleware and calls the gate on the first line of the action; the first such controllers arrive with the security settings, and a test fixture stands in for them here. ADR 0011 keeps core's checks inline because an app may override the action; the middleware entry survives that override, and the inline call survives an app replacing `middleware()`. The gate is idempotent inside a request, so meeting it twice costs nothing and answers the same.
- **A refusal on any route carries the hardening floor.** `AddHardeningHeaders` acts on Keystone routes only. The gate marks the request it refused, and the middleware acts on that mark too, so the redirect and the 403 are hardened on an app's own route without hardening the app's own responses.
- **The intended URL comes from the request, and a mutation is never replayed.** A browser's GET goes back to its own URL. Anything else goes back to the same-origin page it came from, else `/`. Replaying a mutation after the replay would let the sudo page submit a change the user never saw, and the page it came from is where they can make it again.
- **A sudo-in-progress is the other shape of the same session value.** The guard's one sudo key holds a grant or a sudo-in-progress, and one parser turns it into `SudoGrant`, `SudoInProgress` or nothing, so a session can't hold both and a malformed value is nothing held. It lasts a fixed 15 minutes from the refusal that started it, as a pending sign-in does; a later refusal keeps its start time, so asking never buys time, and only a browser's GET replaces the page it returns to. Whether it ran out is decided by the request that reads it, once, before any write: an answer whose sudo-in-progress ran out while the credential was checked is refused and nothing is written. Passing the first step changes the auth level, which rotates the session id, closes the ceremony slots and keeps the start time. The ceremony slots end with it.
- **The replay is a third credential attempt on the existing surfaces.** There is no sudo surface for a method to serve. The first step verifies on the sign-in surface and the second on the challenge surface, through `SudoAttempt`, which shares the proving, ownership and finishing code with the sign-in and challenge attempts. It takes the `SudoInProgress`, so it cannot run for a session nothing was demanded of, and it refuses a type the step doesn't offer before taking a failed attempt, so the page is not a credential oracle. The offer is `SignInDecision::replayOffer()`: the held sign-in types before a first factor, the challenge offer after one. Whether a second step is owed is `SignInDecision::demand()`, the same call sign-in makes, so an account holding a second factor is never granted on its first factor alone, and a type proving two factors is done in one step. A refused or enrollment-owing demand is refused as `keystone.barred`.
- **Its flow is derived, and shares the TOTP count.** `Flow::of()` answers `SUDO` for a signed-in session whose sudo-in-progress is at the surface in use (ADR 0007). Wrong answers count in the `sudo` flow apart from sign-in's, and a guessable type shares its count with the challenge, so a stolen session gets no fresh guesses at a six-digit code.
- **The grant is the last write.** `SudoAttempt::advance()` writes what the proof changed and, on the step that grants, stamps the credential's last use, in one locked account change before the grant, so a lock failure or a lost race ends with no grant. A first factor whose account still owes the challenge earns nothing yet and stamps nothing. `grantSudo()` takes a `Subnet`, which `Subnet::of()` refuses to make from an address that isn't an IP address, so an answer from such an address is counted and refused as `sudo.failed` with `keystone.unbindable_subnet` rather than granted unbound. A rehash goes through `AccountChange::rehash()` after the grant and never moves the epoch.
- **The last recovery code is always kept.** The challenge keeps it only while `require_recovery_codes` is on, because an account that must hold codes must not spend its last one. At sudo the session is already signed in and loses nothing by being refused, so the code that would get it back into the account is kept whatever the setting says.
- **A wrong answer alerts from a known device too.** Whoever answers holds the session or a copy of it. The known-device cookie says the browser signed in before, which is what a stolen session looks like, so it mutes nothing here. No sudo event passes `knownDevice` to the recorder.

## Consequences

- An app gates a route with `['auth', 'sudo']` and nothing else. A JSON client gets a 403 with `reason: sudo` and must send the user to the sudo page itself.
- The response to a refusal is swappable; the gate, the offer and the attempt are not.
- A session refused on one page and then on another goes back to the second page once granted.
- A session whose second factor is removed while it is at the second step is sent on without sudo and starts over at the first step on its next refusal, where it is granted on the first factor alone, as a sign-in would be.
- `Flow::SUDO` exists only while a session is signed in and holds a sudo-in-progress at the surface in use, so a method package never sees it on a guest.
- The `limit.tripped` alert can now follow a sudo trip, so its wording names no flow.
- Method packages that serve the sign-in or challenge surface serve the replay without knowing it. OAuth, magic links and WebAuthn have no packages yet, so their sudo rules in the spec wait for them.
