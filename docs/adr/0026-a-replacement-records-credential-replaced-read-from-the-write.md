# A replacement records credential.replaced, read from the write

ADR 0023 lets a proof say that its credential replaces every credential of its type the account holds, and records `credential.added` for it. A password change and a security key upgraded to a passkey also take the place of what the account held, and the spec records `credential.replaced` for them. This decides how core tells an addition from a replacement without naming a type, and what the user is told after each.

- **The account change reads it from the usable credentials the answer was proved against.** A replacing credential still deletes every credential of its type, disabled ones included. It replaced something only when the account held a usable credential of the type, which `verify()` was given and the lock checks again. That one fact ends the account's other sessions and picks the event: `credential.replaced` when it held one, `credential.added` when it held none, as for an account's first credential of a replacing type or a password added over a disabled one. A disabled credential was no way in, so deleting it signs nobody out. It also returns `SettingsEnrollmentResult::REPLACED` or `ADDED`, so the controller's status, the event and the epoch move come from one fact and can't disagree. The proof needs no new flag.
- **TOTP re-enrollment records `credential.replaced`.** This supersedes ADR 0023's "A replacement records `credential.added` only". The event still names the new credential, and no `credential.removed` is recorded for the one it replaced. `credential.replaced` alerts, with its own mail, because the old credential stopped working and the account's other sessions were signed out.
- **A replacement replaces exactly what it was proved against.** `verify()` is given the account's usable credentials of the type, and a password change is proved against the password it was given. Under the account lock, `AccountChange::enroll()` refuses a replacing credential with `keystone.superseded` when those credentials are no longer exactly the ones the account holds, so two changes proved against the same password apply once, and two first passwords added at once store one. The same-answer check of ADR 0023 runs first, so a TOTP double click still stores one key and refuses nothing, and the second answer reports the outcome the first one had: replaced when it was proved against a usable credential other than the one the first answer stored. A salted hash never matches that check, which is why the comparison is by credential id.
- **A replacement flashes `credential-replaced`.** It says the other sessions were signed out. The `enrolled` status offers to sign out the other sessions, which a replacement already did, so a replacement no longer shows that offer.

## Consequences

- An app that listened for `credential.added` to learn of a new TOTP key also listens for `credential.replaced`.
- The alert for a replaced credential says the account's other sessions were signed out. The alert for an added one doesn't.
