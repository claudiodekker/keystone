# Settings enrollment ends with its sudo and the proof says whether it replaces

A signed-in user adds a credential from the security settings through the same ceremony a held sign-in enrolls with, behind the sudo gate of ADR 0022. This decides what ties that ceremony to the sudo it was started under, where the write is checked, and how a credential that takes the place of an older one, as a new TOTP key does, is stored without core knowing which types do that.

- **A signed-in session's ceremony slots end with its sudo.** A slot already ends with the pending sign-in or the sudo-in-progress that owns it. For a signed-in session it also ends no later than the sudo grant it was opened under, whatever cap its caller gave, and every way a grant ends early (the user ends it, the subnet changes, a new grant is earned) is an auth-level change, which closes every slot (ADR 0021). The guard enforces this, so no controller has to remember it and no later grant ever reads a ceremony an earlier one started.
- **The session keeps what the form can't be drawn from again, and nothing else.** The slot holds what the type's ceremony start returned. Anything the page can draw from that, such as TOTP's QR code drawn from its `otpauth://` URI, is drawn again on each request rather than kept. Kept in the slot, the QR code made the session cookie of the `cookie` session driver 33 KB, which no browser stores, so every reload made a new key and no code could be accepted.
- **The settings write checks the type and the ceremony itself.** The type must be listed on the enrollment surface and the ceremony must be the one the session holds; a caller can supply neither. The answer is proved inside the timing floor and a refused one counts in the `settings` flow, which is derived for a signed-in session on the enrollment surface (ADR 0007). The count is the type's own in that flow, TOTP's included.
- **What can change while an answer is verified is checked again under the account lock.** Verifying takes time, and the timing floor adds more. Inside the locked account change the write checks that the account isn't barred, that the type is still listed on enrollment, and that the session still holds a grant the gate would accept. A barred account and an unlisted type are refusals that keep the failed attempt, as a barred account's does elsewhere. A grant that ended is not a wrong answer: the attempt is given back, nothing is recorded, and the request is refused the way the gate refuses, so the user returns to the type's step once sudo is granted.
- **The proof says that it replaces, and the account change applies it.** A type that is one-per-account, such as TOTP, says in its proof that the new credential replaces the type's others. The account change then deletes every credential of the type the account holds, disabled ones included, before it stores the new one, and ends the account's other sessions only when it deleted one. Core never names TOTP, and no type has to answer a question about itself that most types answer with "no". The delete and the insert sit under the account's row lock, so two enrollments at once leave one credential. An enrollment that is already stored is not applied again: when the account holds a usable credential of the type with the same secret, the same answer arrived twice, as a double click sends it, and the second one changes nothing. Without that, the second would delete what the first stored, move the epoch and alert twice for an account's first credential.
- **An enrollment rotates the session id after the commit, exactly once.** When the epoch moved, the mover's session is already rotated. Otherwise only the id rotates, so the sudo and the slots stay.
- **A held sign-in doesn't replace.** A replacement moves the credential epoch, and a pending sign-in whose account's epoch moved is voided on its next read, so the sign-in would be dropped after its credential was committed. A held sign-in only enrolls an account that holds no usable second factor, so the case is a disabled credential of the same type, which stays beside the new one.

## Consequences

- Earning sudo again starts a new ceremony. A user who lets sudo run out on the TOTP page scans a new QR code.
- A method package makes its type one-per-account through its proof. It writes no delete of its own.
- Enrolling a new TOTP key signs out the account's other sessions. Enrolling an account's first one doesn't.
- The forced flow and the settings flow can leave different rows for the same type: a disabled TOTP credential survives a held sign-in's enrollment and not a settings enrollment.
- What a ceremony start returns for the page is kept in the session until the ceremony ends, so a refresh shows the same thing. A type keeps that small and draws anything large on each request, with the same result for the same ceremony.
