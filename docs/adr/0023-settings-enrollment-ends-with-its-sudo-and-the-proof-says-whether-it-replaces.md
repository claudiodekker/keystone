# Settings enrollment ends with its sudo and the proof says whether it replaces

A signed-in user adds a credential from the security settings through the same ceremony a held sign-in enrolls with, behind the sudo gate of ADR 0022. This decides what ties that ceremony to the sudo it was started under, where the write is checked, and how a credential that takes the place of an older one, as a new TOTP key does, is stored without core knowing which types do that.

- **A signed-in session's ceremony slots end with its sudo.** The guard already ended a slot with the pending sign-in or the sudo-in-progress that owned it. Its phase end for a signed-in session now also folds in the end of a sudo grant. A slot opened under a grant therefore ends no later than the grant, whatever cap its caller gave, and every way a grant ends early (the user ends it, the subnet changes, a new grant is earned) is an auth-level change, which closes every slot (ADR 0021). The rule lives in the guard, so no controller has to remember it and no later grant ever reads a ceremony an earlier one started.
- **One class owns the enrollment slot.** `EnrollmentCeremonies` starts, reads and closes a type's enrollment ceremony for both flows. The slot's key and the shape it stores are named there only.
- **The session keeps what the form can't be drawn from again, and nothing else.** The slot holds what `initiate()` returned: the ceremony and the page's strings. A type whose form shows something it can draw from that page implements `Methods\PresentsCeremony`, and `EnrollmentCeremonies` calls its `present()` every time it reads the slot. TOTP keeps the key and the `otpauth://` URI, and draws the QR code from the URI on each request. Kept in the slot, the QR code made the slot 18 KB and the session cookie of the `cookie` session driver 33 KB, which no browser stores, so every reload made a new key and no code could be accepted. Without it the slot is 740 bytes. The capability is an optional interface, not a method on `CredentialType`, because every other type would only pass its page through.
- **The settings write has one door, which takes the type's name.** `SettingsEnrollmentAttempt` looks the type up on the enrollment surface and reads the ceremony from the session itself, so a caller can hand it neither a type that isn't listed nor a ceremony the session doesn't hold. It proves inside the timing floor and counts a refused answer in the `settings` flow, which `Flow::of()` derives for a signed-in session on the enrollment surface (ADR 0007). The count is the type's own in that flow, TOTP's included.
- **What can change while an answer is verified is checked again under the account lock.** Verifying takes time, and the timing floor adds more. Inside the locked account change the attempt checks that the account isn't barred, that the type is still listed on enrollment, and that the session still holds a grant the gate would accept. A barred account and an unlisted type are refusals that keep the failed attempt, as a barred account's does elsewhere. A grant that ended is not a wrong answer: the attempt is given back, nothing is recorded, and the controller refuses the way the gate does, so the user returns to the type's step once sudo is granted.
- **The proof says that it replaces, and the account change applies it.** `TotpType` enrolls through `EnrolledCredential::replacing()`, which sets `replacesExisting`. `AccountChange::enroll()` then deletes every credential of the type the account holds, disabled ones included, before it stores the new one, and ends the account's other sessions only when it deleted one. Core never names TOTP, and no type has to answer a question about itself that most types answer with "no". The delete and the insert sit under the account's row lock, so two enrollments at once leave one credential. An enrollment that is already stored is not applied again: when the account holds a usable credential of the type with the same secret, the same answer arrived twice, as a double click sends it, and the second one changes nothing. Without that, the second would delete what the first stored, move the epoch and alert twice for an account's first credential.
- **A replacement records `credential.added` only.** Superseded by ADR 0026, which records `credential.replaced` for it. The account still holds a credential of the type, and the event names the new one. No `credential.removed` is recorded for the one it replaced.
- **An enrollment rotates the session after the commit, exactly once.** `AccountChange::enroll()` asks for a rotation. When the epoch moved, `carryOver()` already rotates the mover's session. Otherwise `AccountChanges` calls `KeystoneGuard::rotateFor()`, which rotates the id and nothing else, so the sudo and the slots stay.
- **A held sign-in doesn't replace.** `EnrollmentAttempt` keeps storing with `addCredential()`. A replacement moves the credential epoch, and a pending sign-in whose account's epoch moved is voided on its next read, so the sign-in would be dropped after its credential was committed. A held sign-in only enrolls an account that holds no usable second factor, so the case is a disabled credential of the same type, which stays beside the new one.

## Consequences

- Earning sudo again starts a new ceremony. A user who lets sudo run out on the TOTP page scans a new QR code.
- A method package makes its type one-per-account by enrolling through `EnrolledCredential::replacing()`. It writes no delete of its own.
- Enrolling a new TOTP key signs out the account's other sessions. Enrolling an account's first one doesn't.
- The forced flow and the settings flow can leave different rows for the same type: a disabled TOTP credential survives a held sign-in's enrollment and not a settings enrollment.
- What `initiate()` returns for the page is kept in the session until the ceremony ends, so a refresh shows the same thing. A type keeps that small and draws anything large in `present()`, which must give the same result for the same page.
