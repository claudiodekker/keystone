# Sudo is one session value that every auth-level change drops

A change to how an account signs in should rest on a proof made moments ago, not on a session that may be twelve hours old or restored by a cookie. Sudo is that proof's lifetime: a short grant on the signed-in session. The grant is security state like the sign-in itself, so the same questions apply to it. Where does it live, who may write it, and what makes sure a stale one never survives?

- **The guard owns it, in one session key.** `keystone_sudo_<guard>` holds `granted_at` and the subnet, next to the epoch and the sign-in time (ADR 0005). Only `KeystoneGuard` reads or writes the key, and it hands the rest of core a parsed `SudoGrant`, or null. The key holds one value, so whatever sudo state a later step adds takes its place rather than sitting beside it, and a session can't hold two answers to "does it have sudo".
- **One method writes a grant, and it takes a subnet.** `stampSudo(Subnet $subnet)` is the only write of `granted_at`. Reading a grant never stamps it again, so it can't slide: it ends `sudo.lifetime_seconds` (15 minutes) after it was stamped, however busy the session is. The lifetime is added when the grant is read, so lowering the setting shortens grants already held. A grant whose time is in the future is forgotten, as a session's sign-in time is (ADR 0013).
- **Every change of auth level drops it.** `changeAuthLevel()` already rotates the session id and closes the ceremony slots. It now forgets the sudo key as well, so holding a sign-in, passing a second factor, signing in, restoring from a remember-me cookie and ending sudo all drop a grant in the one place they share. Sign-out, expiry and demotion invalidate the whole session. A flow added later drops the grant by changing the auth level the way every other does, with nothing to remember. The case that needs it today is a session that outlived its absolute lifetime and is restored by its cookie (ADR 0020): the session's data is kept, and without the drop a grant a minute old would be carried into a session nobody proved anything for.
- **The mover's session keeps it.** A user's own change that ends their other sessions re-stamps and rotates their session through `carryOver()`, which is not an auth-level change (ADR 0014). They just proved who they are to make that change, so their grant stays.
- **Only a real sign-in brings it.** `signIn()` stamps the grant after it starts the session, so every flow that completes a sign-in brings sudo without asking for it: the first factor, the challenge and the enrollment. `signInRemembered()` never stamps a grant. It shares only the start of the session with `signIn()`, and that step drops any grant the session held. The guard records `sudo.granted` with the reason `keystone.sign_in` itself, as it records the remembered return, so no flow can bring a grant without the row.
- **A grant is bound to a subnet, and none is made without one.** `Subnet::of()` is the only code that parses an IP address for sudo: the /24 of an IPv4 address, IPv4-mapped IPv6 unwrapped first, else the /64. It returns null for anything else, and `stampSudo()` can't be called with null. A sign-in from an address that can't be parsed completes with no grant and no `sudo.granted`, rather than failing the sign-in or holding a grant that any network could use. Binding to the whole address would end the grant every time a phone or an IPv6 privacy address changed. Binding to nothing would let a copied session cookie carry sudo to any network.
- **Ending sudo is an auth-level change.** `DELETE sudo.end` rotates the session id and closes the slots like any other, and records `sudo.revoked` only when a live grant was ended, so repeating the request adds nothing to the trail.

## Consequences

- A grant lives and dies with its session. There is no table, no index of grants and no way to list or revoke another session's grant, except by ending that session.
- An account whose requests reach the app from an address that isn't an IP address, such as behind a proxy that isn't trusted and passes a hostname, never has sudo after signing in.
- Behind a load balancer whose address the app doesn't resolve to the client's, every grant is bound to the balancer's subnet, and the binding stops telling networks apart.
- `sudo.granted` adds one row to the account's trail for every sign-in.
- Lowering `sudo.lifetime_seconds` takes effect for grants already held. Raising it revives a grant that had run out but whose session nothing has read since.
