# Owed enrollment is read from holdings and demotes signed-in sessions

Both mandates default on: every account must hold a second factor and recovery codes. Whether an account owes enrollment has to be known on every request that asks who is signed in, because a mandate turned on, or a second factor removed, must not leave a signed-in session that skips it. Counting credentials and codes on every request would add two queries to every page.

- **Holdings are read, not stored.** Whether an account holds a second factor and recovery codes is asked of its credentials and codes when a request needs to know, and only while the mandate that cares is on. Nothing is kept beside the source, so nothing can drift from a write that went around the account change unit, and turning a mandate on or off needs no backfill. A credential counts as a held second factor when its type is listed in `keystone.methods` on the `challenge` surface, and that is the only way the second-factor mandate is met: a type that proves two factors on its own, like a passkey, must serve the challenge, or its holders enroll a second factor like anyone else. So a password sign-in of an account holding a passkey is challenged for it rather than let in on the password alone, and the guard asks the same question of a signed-in session as the sign-in asked of the proof, so the two can't disagree. Enrollment offers only types that answer the challenge, since a credential that can't would leave a password sign-in owing a challenge nothing answers. A disabled credential and a spent code don't count. Unlisting a type is the app changing, so its credentials stop counting, stay stored, and count again when the type is listed again; with the mandate on their users enroll again.
- **The decision stays one module.** `SignInDecision` decides the challenge, enrollment and sign-in, at the first factor and again for a pending sign-in as its account stands now, before and after each enrollment step. A second factor added elsewhere while a sign-in is held at enrollment drops the held sign-in, even once its recovery codes were saved, and the user signs in again and answers the challenge, because a pending sign-in remembers whether it passed one and never passes on a factor it didn't prove.
- **A signed-in session that newly owes is ended, not held.** Nothing a session enrolls may rest on an earlier sign-in: a stolen cookie must not add its own authenticator, and a session that skipped the challenge must not mint break-glass codes. So the guard ends the session as it does an expired one, with `Clear-Site-Data`, records `session.ended` with reason `demoted`, and sends the user to sign in again with the page they asked for kept as the intended URL. The normal sign-in then proves the first factor, the challenge when the account holds a second factor, and only then the enrollment. A JSON client gets a 401 with reason `demoted`, so it can tell owing enrollment from an expired session. The response is a swappable action, `RespondToDemotedSession`. Signing out of such a session ends it the same way. Parallel requests of one such session each end it and may each record the event.
- **Enrollment writes once.** The credential and `credential.added` commit in one account change that moves no epoch, after the ceremony's answer is verified. Inside the lock the change refuses an account that is barred, that left the pending sign-in's credential epoch, or that already holds a second factor, and the recovery-code change one that already holds codes, so concurrent answers store one credential or set, a held sign-in can't add its own factor after another enrolled first, and a request that outran a password change elsewhere writes nothing. A rejected answer writes nothing, and the ceremony is forgotten as the change commits.
- **Recovery codes are staged in the session.** The set lives in a ceremony slot until the user types one back, so a reload shows the same codes and nothing is stored that the user never saw. A first set alerts nobody; replacing a set ends the account's other sessions and alerts.

## Consequences

- A passkey type that doesn't serve `challenge` doesn't count as a held second factor: its holders' password sign-ins aren't challenged for it, and with the mandate on they enroll a second factor that does serve it. The passkey package must serve `challenge`.
- Credentials of an unlisted type stay stored and count again when the type is listed again. No command prunes them yet.
- While the mandates are on, every authenticated request asks the database whether the account holds a second factor and recovery codes: up to two indexed lookups, once per request.
- Turning a mandate on signs every session that doesn't meet it out on its next request. Users type their first factor again before they enroll.
- Production refuses to boot with `require_second_factor` on and no listed type that can be enrolled as a second factor, so no account can be held at a step it can't finish.
