# A known device is a re-keyed cookie that only splits failed attempts

A sign-in from a browser the account hasn't used should alert its owner, and failures from an attacker's browsers shouldn't lock the owner out of their own. Both need Keystone to recognise the owner's browser, and an IP address or user agent can't: the attacker can copy a user agent and share a network.

- **A known device is a cookie.** Each sign-in hands the browser `__Host-keystone_device`: 128 random bits that name the device and never change, a dot, and 256 random bits that every sign-in replaces. Keystone stores the SHA-256 digest of the whole value and of the device part per account, with the user agent and IP address as encrypted display labels. Nothing else decides: a new IP on a known browser doesn't alert, and a new browser on a known IP does. A plain digest is enough for a random value nobody can guess, so `keystone:rekey` has nothing to recompute for it. Laravel doesn't encrypt the cookie, since its digest is all the server checks and a value it never handed out matches nothing.
- **Every sign-in re-keys.** The browser gets a fresh value at each sign-in, and every account row holding the old digest moves to the new one. A copied or planted value is known only until that browser's next sign-in, after which it matches nothing and its sign-ins alert. Accounts sharing a browser keep knowing it, because they move with it.
- **A replaced value that comes back means a copy.** A sign-in whose cookie names a device of the account but carries a value a later sign-in replaced comes from one of two browsers sharing a cookie. Keystone can't tell which of them is the owner's, so it records `device_cookie.reused`, which alerts the owner, and the account's row follows the browser that signed in. The other browser now holds the replaced value, so its next sign-in alerts the same way: the owner hears of every sign-in from the copy for as long as it can sign in. The device part is what makes this work however often the copy signed in first. Each account that knew the device is told at its own next sign-in, and only its own row changes, so knowing a device part lets nobody touch another account's device. A device unseen for the retention is new again here too. It doesn't alert at the moment a copy signs in first: only the IP address could show that, and an address changes too often for the owner (IPv6 privacy addresses, phones, shared egress pools) to carry an alert anyone would keep reading.
- **Known means seen within the retention.** A device unseen for `retention.known_devices_seconds` (90 days) is new again, whether or not the nightly prune has deleted its row yet, so the alert never waits on the scheduler.
- **It only splits failed attempts.** The failed-attempt count of a known device's browser is keyed by the id of its row, the rest by `other`, each with the full allowance. The id outlives re-keying where the digest doesn't: keyed by the digest, a browser two accounts know could spend one account's allowance, sign in to the other, and start again at zero under its new value. That is lockout immunity and nothing more: a known device is challenged, limited and alerted about like any other browser. Being known is checked against the account the attempt names, so a value another account knows counts as `other`.
- **The guard runs the check.** `KeystoneGuard::signIn()` reads the cookie, decides whether it was known, re-keys and queues the new cookie before it touches the session, and returns the verdict. Every flow that completes a sign-in records it as `signed_in`'s `known_device`, and the recorder sends no alert about an event from a known device. A failure to write the device row fails the sign-in rather than signing in without an alert.

## Consequences

- A failed-attempt trip alerts the account's owner once per count and window, through the `limit.tripped` slot. A request-limit trip records the event and alerts nobody, since it names no credential and a busy shared network would mail the owner for nothing.
- Each known device adds one indexed lookup to a sign-in attempt that names an account, inside the timing floor.
- An operator ending an account's sessions forgets its devices, and `--all` forgets every account's, so a cookie an attacker held stops counting apart and the owner's next sign-ins alert. Other changes that end sessions, such as replacing recovery codes or suspending, keep the devices: they don't say a browser was compromised.
- The prune is a scheduled closure rather than a queued job, so it runs without a queue worker.
- The known-device check reads outside the account's lock, so a sign-in racing an operator's end-sessions can write its device row after the forget. Its session still dies on the epoch.
- A sign-in whose response never reached the browser leaves it holding a replaced value, so its next sign-in alerts as reused though nothing was copied. Two sign-ins sent at once from one browser, such as a form submitted twice, do the same for the one handled second.
- The sign-in that ends registration or recovery will be exempt from the alert when those flows land; until then every new device alerts.
