# A remembered return restores the full sign-in

A user who ticks "Remember me" expects to come back signed in. NIST SP 800-63B says otherwise for an account with a second factor: at AAL2 the user authenticates again at least every 12 hours and after 30 minutes of inactivity (revision 3, section 4.2.3). ASVS 5.0 V7.3.2 asks for an absolute session lifetime that enforces re-authentication, and V7.1.1 asks that any deviation from the NIST re-authentication requirements is justified in writing. This is that justification.

- **A remembered return is a full sign-in, with no factor asked.** A browser holding a live `__Host-keystone_remember` cookie and no signed-in session is signed in again as its account, for up to `remember.lifetime_seconds` (30 days) after the sign-in that issued the cookie. We accept the deviation because the alternative is the one users work around: an app that asks for a password and a code every morning teaches its users to pick weak ones, and an app that wants the NIST behaviour sets the lifetime to `0`. What bounds the cookie instead is that the user asked for it, that it only exists after a sign-in that proved every factor the account holds, and that its lifetime is fixed.
- **The lifetime is written on the token when it is issued, and nothing extends it.** Each `user_remember_tokens` row holds the SHA-256 digest of its cookie's 256 random bits, the credential epoch of the sign-in and an expiry. A return checks them on the server and writes nothing, so using the cookie daily buys no extra day, and raising the setting later does not lengthen a secret already in a browser.
- **The absolute session lifetime still applies, to the session.** A session restored by the cookie gets an absolute lifetime of its own (ADR 0013), counted from the restore. When it passes and the cookie is still live the session is restored again, on a new session id, with no `session.ended`, no `Clear-Site-Data` and no notice. Nothing ended for the user, and `Clear-Site-Data` naming `cookies` would delete the cookie that just restored them. `signed_in` with the reason `remembered` is the record.
- **The credential epoch and the account's state still kill it.** A token from an older epoch, or of a suspended, invalidated or deleted account, never restores. Its row and cookie are deleted when it is presented and `request.rejected` is recorded with the reason `keystone.dead_remember_cookie`, against the account when the row was found.
- **A return whose account newly owes enrollment is refused, not held at enrollment.** The v4.0 spec (#22) and the remember-me ticket (#43) said such a return "lands at enrollment". ADR 0018 already decided that nothing a session enrolls may rest on an earlier sign-in, because a stolen cookie must not add its own authenticator, and a 30-day bearer cookie is exactly that stolen cookie. So the token and cookie are deleted, the `enrollment-owed` status is flashed, `request.rejected` is recorded with the reason `keystone.enrollment_owed`, and the user signs in again and enrolls after the challenge, as a demoted session does. A demoted session forgets its own token for the same reason. The cost is that such a user types their first factor once more and ticks the box again.
- **A return reads the device cookie and never re-keys it, and the remember-me value is not re-keyed either.** The v4.0 spec said a remembered return mints a fresh device value like any sign-in. A browser that reopens with several tabs sends several requests with no session at once. Re-keying either cookie on the first would make the second look like a replaced value (ADR 0019) and mail the owner `device_cookie.reused` on an ordinary morning, or sign the second tab out. A return therefore changes no row and sets no cookie, so any number of them may run at once. The cost is that someone who copies the whole cookie jar, remember-me and device cookie together, restores without an alert until the owner's next real sign-in from that browser. A stolen live session cookie has that same exposure today. A copy of the remember-me cookie alone alerts as a new device.
- **The user's own epoch move re-keys their token.** When a signed-in user changes something that ends their other sessions, their browser gets a new remember-me value on the same row, with the same id and expiry, so a copy of the old value dies with the other sessions. This is the one write to a token after its issue, and it happens at a deliberate change, never on a return.
- **A lifetime of `0` turns it off, and the cookie is then not read.** Nothing is issued, the box is hidden, and a cookie issued earlier is ignored rather than deleted. Deleting would record a refusal against every remembered account after a config change, for no gain.

## Consequences

- An account with a second factor can stay signed in on a browser for 30 days without proving either factor again. An app that must meet the NIST limits sets `remember.lifetime_seconds` to `0`.
- Turning the setting back on inside a token's lifetime lets that token restore again. Moving the credential epoch, as `keystone:end-sessions` does, is how to kill tokens at once.
- Tokens of other devices are not deleted when the epoch moves or the account is barred. Each dies, and its row goes, when its cookie is next presented. Rows whose browser never returns stay until a prune is added.
- A full copy of a browser's cookies is not detected at a return. Detecting it needs the values to rotate with a grace window, on both cookies.
- A return from a browser whose device row aged out of `retention.known_devices_seconds` alerts as a new device, because a return does not refresh the row. The default lifetime (30 days) is well inside the default retention (90 days).
- Each request that restores records its own `signed_in`, so several tabs opening at once leave several rows.
- The guard restores only once the session has started, so code that asks who is signed in before `StartSession` runs sees a guest. Restoring earlier would leave the sign-in on the session id the browser sent.
- The restore fires Laravel's `Login` event with `remember` true, and `Auth::viaRemember()` answers true for the request that restored.
