# One account-change unit is the only write door

Every write to an account's credentials, addresses or credential epoch is its own Action (`SuspendAccount`, `EndSessions`, `AddCredential`, …) whose `handle()` runs through one shared trait, `Actions\Concerns\ChangesAccounts`. The trait's `changeAccount($account, fn (AccountWrite $write) => ...)` runs the same steps every time: lock the account's row, read the alert recipients, apply the write, commit, then carry the mover's session over and record the write's events. The write's state lives on the `AccountWrite` it hands the closure, never on the Action, so Actions stay stateless. On it, `endSessions()` moves the epoch (once, however often it is called), `record()` queues an event and `update()` writes the row. Every write that removes, replaces or ends something calls `endSessions()`. A write started inside another write to the same account, such as an Action calling another Action, joins it: one lock, one epoch move, one carry-over, and its events are recorded when the outer write commits.

Holding every write to one table-driven test of which writes move the epoch, and failing that test when a class using the trait has no row in it, means a later write can't forget to end the other sessions after removing a credential without the build going red. Recording after commit means a change that rolls back, including inside a transaction the caller opened, leaves no audit entry and alerts nobody. Reading recipients before applying means an address the change removes still hears about it.

## Consequences

- Callers inject the Action and call `handle()`: commands through `handle()` injection, `SignInAttempt` through its constructor. There are no jobs for these writes: each is a few queries, and the alerts it sends are already queued.
- The operator Actions (`EndSessions`, `SuspendAccount`, `UnsuspendAccount`) are Swappable: an app may bind its own subclass. The lock, epoch move and recording stay in the trait, and the AppTests in `Flows/AccountWritesTest` fail inside the app when a swap stops moving the epoch, barring sign-in or recording. `SignInAttempt` constructs `RehashCredential` itself, so a rehash inside sign-in can't be swapped.
- Ending every account's sessions is one bulk update in the `EndEverySession` Action, not a write to one account, so it doesn't use the trait.
- Which changes move the epoch is one table-driven test through the unit (`ChangesAccountsTest`). A class in any package's `src` that uses `ChangesAccounts` without a row fails that test. Each later ticket that adds a change adds its row: removing a credential or unlinking OAuth, a key-to-passkey upgrade, regenerating recovery codes over a live set, a password change or removal, sign out others, suspension, deletion and completed recovery move it; adding a credential, a first password or first codes, a rehash, revoking one session, a sudo grant, a restore and unsuspending don't.
- The mover's own session survives: when the change moves the epoch and the current session was signed in as the account on the epoch that moved, it is re-stamped with the new one and its id is rotated. A session already on an older epoch is not revived.
- Operators end sessions with `keystone:end-sessions {user}` or `--all`, or by calling the `EndSessions` / `EndEverySession` Actions from an admin panel. Keystone doesn't authorize either; the app decides who may run them.
- `sessions.terminated` is recorded with actor `operator` and the operator the command or Action names, in a fixed `operator` field (cut to 64 characters, control characters replaced), since events carry no free-form metadata.
- `--all` moves every account's epoch in one query, the operator's own session included, and records one `sessions.terminated` about nobody, with reason `keystone.every_account`. Like every event about nobody it is a log line only, not a row on each account's trail, so ending every session costs one update however many accounts there are.
- Ending an account's sessions doesn't yet forget its known devices: they don't exist yet, and arrive with their own ticket (#41), which hooks into the unit. It alerts the owner at the recipients the unit read before the change, unless the operator suppresses it (ADR 0015).
- Owes state doesn't exist yet either; the unit recomputes it once the owed-challenge and enrollment tickets add it.
